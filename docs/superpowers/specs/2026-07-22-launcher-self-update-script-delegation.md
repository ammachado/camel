# Camel CLI Launcher: Self-Update via Script Delegation (Alternative Mechanism)

Date: 2026-07-22
Status: Draft (alternative — compare against `2026-07-21-launcher-self-update-design.md` before choosing one)

## Relationship to the baseline design

This document replaces exactly one component of `2026-07-21-launcher-self-update-design.md`
(the "baseline design"): **how `SelfUpdateCommand` performs the update once it has decided one is
needed** — baseline update-sequence steps 3-8 (download archive, verify checksum, validate
entries, extract, smoke-test, activate). Everything else in the baseline is unchanged and not
repeated here: `InstallDetector`, `UpdateChecker`, `DoctorCommand` and its environment banner, and
the entire Homebrew `apache-camel` rename/distribution section. Read the baseline first.

## Problem

The baseline design re-implements, in Java, a pipeline that `install.sh`/`install.ps1` already
implement today: fetch manifest, download the versioned archive, verify its SHA-256, reject
unsafe archive entries (absolute paths, `../` traversal, symlinks/hardlinks, multiple top-level
roots), extract, smoke-test the staged launcher, and atomically activate it — including
`--version X.Y.Z` for both upgrade and downgrade. Concretely, in this checkout:

| Baseline step | `install.sh` | `install.ps1` |
|---|---|---|
| Fetch manifest/archive | `fetch()` (`install.sh:67-85`) | `Save-RemoteFile` (`install.ps1:72-79`) |
| Verify checksum | `sha256()` (`install.sh:87-98`) | inline `Get-FileHash` (`install.ps1:270`) |
| Validate archive entries | `validate_tar()` (`install.sh:160-197`) | `Test-ArchiveEntry` (`install.ps1:134-177`) |
| Smoke-test staged launcher | `verify_staged()` (`install.sh:199-205`) | `Test-StagedLauncher` (`install.ps1:181-191`) |
| Atomic activate | `activate()` (`install.sh:207-221`) | `Set-CamelShim` (`install.ps1:193-212`) |
| Upgrade/downgrade to a specific version | `--version` (`install.sh:223-239,251-265`) | `-Version` (`install.ps1:18-19,242-244`) |

Keeping two implementations of checksum verification, traversal/symlink rejection, and atomic
activation in sync — one in POSIX shell, one in PowerShell, one in Java — is duplicated logic that
must evolve together forever. This is the same category of risk Rule 2/3 (simplicity, don't
duplicate what already works) flags. This alternative asks: since the scripts already do this
safely, why not have `camel self-update` invoke them directly instead of re-deriving the same
logic a third time?

## Goals

Same as the baseline's goals, plus:

- Eliminate the duplicate Java implementation of archive verification, extraction, and activation.
  The behavior users see (loud failures, atomic activate, smoke-test-before-activate, `--version`
  support, refusal on non-web-installer installs, `--check` reporting) must be identical to the
  baseline design — this is a mechanism change, not a behavior change.
- Any fix to archive-handling safety (e.g. a new traversal edge case) only needs to land in
  `install.sh`/`install.ps1`, not in three places.

## Non-goals

Same as the baseline's non-goals. In particular, this alternative still does **not** modify
`install.sh`/`install.ps1`'s own behavior or flags — it only changes how `SelfUpdateCommand`
invokes them.

## The catch: the installed CLI does not carry a local copy of the scripts

`src/main/assembly/launcher-content.xml` (the shared assembly component for both the public and
WinGet archives) packages `README*`/`LICENSE*`/`NOTICE*`, `bin/*.jar`, `bin/camel.sh`,
`bin/camel.bat`, and `examples/*` — **not** `src/install/install.sh` or `install.ps1`. Confirmed
independently in `camel-package.sh:189-249`: at release time, those two files are copied straight
from `src/install/` to the *website* staging directory (`WEBSITE_DIR/install.sh`,
`WEBSITE_DIR/install.ps1`, byte-identity asserted via `cmp -s`), not into the release archive.

So a running `WEB_INSTALLER` installation has no local copy of either script to shell out to.
Delegation means fetching the script fresh over HTTPS from the website at self-update time — the
same origin already trusted for the manifest and archive, but a materially different trust act:
today's design only ever unpacks a checksummed **archive**; this alternative additionally
*executes freshly downloaded code* with no existing integrity check on that download.

### Proposed fix: a small, additive companion checksum file

Add a new file published alongside the existing manifests, `<manifest_base_url>/install.sha256`,
generated by `WebsiteManifestGenerator` at the same point it already copies the scripts to
`WEBSITE_DIR` (so hashing them is nearly free — the source of truth `cmp -s` already asserts is
byte-identical to what's served). Two lines:

```
install_sh_sha256=<64-hex>
install_ps1_sha256=<64-hex>
```

This is deliberately **not** a change to the existing `latest.properties`/`X.Y.Z.properties`
manifest format: `install.sh`'s `parse_manifest()` fails loudly on any unknown key and requires
*exactly* four lines (`install.sh:118-150`); adding fields there would break every currently
deployed `install.sh`/`install.ps1` the moment a new release published a 6-line manifest. A
separate, purely additive file avoids that entirely and keeps the baseline's "no changes to
install.sh/install.ps1" non-goal intact.

## Components (revised)

### `SelfUpdateCommand` (revised)

Refusal guard (non-`WEB_INSTALLER` detection) is unchanged from the baseline.

1. Fetch and parse the manifest via `ManifestFetcher` (unchanged from baseline) and compare
   against the running version, exactly as baseline steps 1-2 describe. This is still needed in
   Java: neither script has an "already current, skip the download" fast path — both download
   unconditionally every time they run — so without this pre-check, `camel self-update` on an
   already-current install would silently do a full network round-trip for nothing. `--check`
   stops here, as in the baseline.
2. If an update is due (or `--version` was given): download `install.sha256`, download the
   platform-appropriate script (`install.sh` on POSIX, `install.ps1` on Windows) from the same
   website root, and verify it against the matching hash. Fail loudly, exit unchanged, on
   mismatch or missing file — same posture as a checksum failure anywhere else in this feature.
3. Invoke the verified script via `ProcessBuilder`, **always passing the resolved version
   explicitly** (`install.sh --version X.Y.Z` / `install.ps1 -Version X.Y.Z`), never relying on
   the script's own `latest.properties` fallback — even when the user ran plain `camel
   self-update` with no `--version`. This closes a TOCTOU gap that pure delegation would otherwise
   have: without pinning, a new release could land in the window between step 1's version compare
   and step 3's invocation, and the script would silently install a version `SelfUpdateCommand`
   never actually decided on.
4. Stream the child process's stdout/stderr straight through (`ProcessBuilder.inheritIO()` or
   redirected passthrough) and propagate its exit code as `camel self-update`'s own exit code —
   no re-parsing of the script's own error text, matching the "fail loud" posture Rule 12 and the
   baseline both require. The script's own final line (`Installed Camel CLI X.Y.Z to ...`) becomes
   the user-visible success message verbatim; no duplicate success message is printed on the Java
   side.
5. POSIX invocation: `sh <staged-script-path> --version X.Y.Z` — the script is passed as an
   argument to `sh`, not executed directly, so no `chmod +x` step is needed on the just-downloaded
   file. Windows invocation: `powershell.exe -NoProfile -ExecutionPolicy Bypass -File
   <staged-script-path> -Version X.Y.Z` — `-ExecutionPolicy Bypass` scopes only to this one
   process invocation (a standard flag; it does not alter the machine/user execution-policy
   setting), the same pattern other Windows package managers use to run unsigned installer
   scripts they ship.
6. Cleanup ("cleans" in the original framing of this alternative): no dedicated cleaning step is
   actually needed beyond deleting `SelfUpdateCommand`'s own staging directory (holding the
   downloaded script + `install.sha256`) after the subprocess exits. `install.sh` already traps
   `EXIT INT TERM` to remove its own staging directory (`install.sh:241-249`), and both
   `activate()`/`Set-CamelShim` unconditionally remove any pre-existing target version directory
   before moving the new one into place (`install.sh:213`, `install.ps1:198-201`) — so a
   half-written directory left behind by a previous crashed attempt is already safely overwritten
   on the next run. Nothing new needs to be built for that.

### `ManifestFetcher` (unchanged responsibility, smaller footprint)

Still needed, but only for the pre-flight version-compare/`--check` path (step 1 above). It no
longer hands its result to a Java-side download/verify/extract/activate pipeline, because that
pipeline no longer exists — the parsing/validation logic itself (four required keys, format check,
version format, checksum format) is identical to the baseline's description.

## Data flow summary

```
camel self-update [--version X.Y.Z | --check]
  -> InstallDetector.locate() -- refuse if not WEB_INSTALLER
  -> ManifestFetcher.fetch() -- compare versions, stop here if --check or already current
  -> download install.sha256 -> download install.sh|install.ps1 -> verify checksum
  -> invoke script via ProcessBuilder, pinned to the resolved version
  -> passthrough stdout/stderr and exit code
```

## Error handling (revised rows only — see baseline for the rest)

| Situation | Behavior |
|---|---|
| `self-update`: `install.sha256` missing or malformed | Fail loudly, exit non-zero, no script invoked |
| `self-update`: script checksum mismatch | Fail loudly, exit non-zero, no script invoked |
| `self-update`: script exits non-zero | Passthrough exit code, script's own stderr already explains why (it fails loudly itself — see `fail()`/`Fail` in both scripts) |
| `self-update`: script exits zero | Treated as success; no separate Java-side verification of the result |

## Comparison with the baseline design

| | Baseline (native Java) | This alternative (delegate) |
|---|---|---|
| Archive verify/extract/activate logic | Re-implemented in Java | Reused from `install.sh`/`install.ps1` |
| External process dependency | None (pure `java.net.http.HttpClient` + `java.util.zip`) | `sh` on POSIX, `powershell.exe` on Windows |
| New manifest/checksum surface | None | New additive `install.sha256` file |
| TOCTOU between version-check and install | N/A (Java does both in one pass) | Must explicitly pin `--version`/`-Version` (see above) — otherwise present |
| Java test surface for archive handling | Full unit coverage of traversal/symlink/checksum cases | None needed — inherited from the scripts' own existing coverage |
| Failure messages | Authored directly in Java | Whatever the script already prints |
| Works in environments without a shell/PowerShell (e.g. hardened containers) | Yes | No — same floor the *initial* `install.sh`/`install.ps1` already require, so no regression for a `WEB_INSTALLER` install, but a real constraint if that ever changes |

The last row is the strongest argument for the baseline: it's not actually adding a new
dependency versus what a `WEB_INSTALLER` install has already required since the machine's
*first* install. Self-update running under the same conditions as the original install isn't a
new floor.

## Open items to verify during implementation

- Exact publish path for `install.sha256` relative to `manifest_base_url` (same directory as
  `latest.properties`, most likely).
- Confirm the target PowerShell floor: `install.ps1`'s BOM-avoidance comment
  (`install.ps1:207-209`) already implies Windows PowerShell 5.1 compatibility is a requirement
  for the *existing* installer; self-update inherits that floor rather than introducing a new one.
- Decide whether `ProcessBuilder` output should be captured and re-emitted (to prefix/tag it as
  coming from the installer) or truly inherited 1:1 — inheriting is simpler and was assumed above,
  but capturing would let `camel self-update` add its own structured logging around it.

## Testing (revised — see baseline for what's unchanged)

- Unit tests for the new `install.sha256` fetch/verify step (missing file, malformed lines,
  checksum mismatch).
- Process-invocation tests asserting correct interpreter/flags per OS, correct
  `--version`/`-Version` pinning (never omitted, even for a bare `camel self-update`), exit-code
  passthrough, and stdout/stderr passthrough — using a fake stand-in script at the test's
  `CAMEL_SELF_UPDATE_MANIFEST_BASE_URL`-equivalent seam so no real network or global machine state
  is touched.
- Integration test: end-to-end `camel self-update` against a local `HttpsServer` serving a fake
  manifest, `install.sha256`, and the **real** `install.sh`/`install.ps1` from this repo, asserting
  the script actually runs and installs into a temp `HOME`/`XDG_DATA_HOME` — this exercises the
  real scripts rather than a Java re-implementation of their behavior, which the baseline's
  equivalent test cannot do.
- Dropped versus the baseline: dedicated Java unit tests for archive-entry validation
  (traversal/symlink/multi-root rejection) — that logic doesn't exist in Java anymore; it's
  exercised for free by the integration test above running the real scripts, and by whatever
  existing test coverage `install.sh`/`install.ps1` already have for `install.sh`/`install.ps1`
  themselves.
